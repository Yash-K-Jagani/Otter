# E1100 — undischarged contract

A contract clause is not proved.

## Cause

A `requires`, `ensures` or loop `invariant` states something the verifier has
to establish, and the verifier could not. A contract is a promise about every
call, not a comment: a `requires n > 0` says the function is only ever called
with a positive `n`, and a call site that cannot show `n > 0` is the mistake
the clause exists to catch.

The verifier reasons about integers with an interval and a congruence: it
knows what a literal is, what a parameter's type allows, what an assignment
wrote, and what a branch or a loop condition proved. It does not know what a
call returns, what a field holds, or what a division yields. A clause that
depends on one of those is unproved, and an unproved clause is reported.

The clause is enforced: an unproved `requires`, `ensures` or `invariant` is an
`error`, and `verify`, `build`, `run` and `test` all refuse the program. A
contract is not a hint or a comment, so a build that cannot establish one is a
build of a program that may break its own promise.

## Example

```yashy
fn positive(n: int) -> int requires n > 0 {
    return n;
}

fn main() {
    let x = positive(-1);
}
```

```text
contract.ya:6:15
error[E1100]: cannot prove the precondition `n > 0` of `positive`
    let x = positive(-1);
              ^^^^^^^^^^^ this clause is not proved
  docs: https://yashy.dev/errors/E1100
```

The same diagnostic names the obligation (`requires`, `ensures` or
`invariant`), the fact it could not establish, and the clause's source text, so
the fix is local to the call or the function it names.

## Fix

Make the fact provable where the verifier can see it:

- pass an argument whose range implies the clause, such as `positive(1)`;
- add a `requires` to the caller so the fact is assumed at the top of its body
  and owed by its own callers;
- check the value before the call, so the branch narrows it:
  `if n > 0 { positive(n); }`;
- for an `ensures`, add a `requires` that implies it, or return a value the
  domain can see, such as a literal or a parameter the clause bounds;
- for an `invariant`, establish it before the loop and leave it true at every
  `continue` and at the end of the body.

If a clause is true but the domain cannot see why, simplify it or move the
fact into a `requires` that says exactly what the proof needs.
