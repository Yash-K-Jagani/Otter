# E1201 — provable integer overflow

Checked integer arithmetic always overflows.

## Cause

Integer `+`, `-`, `*` and unary `-` are **checked**: an operation whose
mathematical result does not fit in `int` stops the program with a message and
a position instead of continuing with a wrong number. When the verifier can
show that *every* result the operands can produce is outside the `int` range,
the program cannot get past that line, so it is reported before it is built.

The verifier reasons about integers with an interval and a congruence. A literal
is exact, a `for` loop's variable has its range, a branch narrows a binding, and
an assignment records what it wrote. The rule fires only when the whole result
range is out of bounds:

| Operand ranges | Result range | Verdict |
|---|---|---|
| `x` is `9223372036854775807` | `x + 1` is `9223372036854775808` | reported |
| `a` and `b` are any `int` | `a + b` may or may not fit | not reported |
| `i` is `0..3` | `i + 1` is `1..4` | not reported |

A "may or may not" is a runtime check that stays: the program builds, and it
faults only if the operation really overflows when it runs. This is deliberately
stricter than indexing, where an out-of-range access is a defined `None` rather
than a fault: an overflow here is a certain fault, not a value.

## Example

```yashy
fn main() {
    let x: int = 9223372036854775807;
    let y = x + 1;
}
```

```text
overflow.ya:3:13
error[E1201]: `x + 1` always overflows: every result is outside the range of `int`
    let y = x + 1;
            ^^^^^ this operation always overflows
  docs: https://yashy.dev/errors/E1201
```

`--json` carries the same fact as a proof trace, naming the obligation
(`overflow`) and what would have made the operation safe.

## Fix

Say what the program means. The language has nine operations for the three
cases, `wrapping_*`, `checked_*` and `saturating_*` over `add`, `sub` and `mul`:

- **Wrap.** `wrapping_add(x, 1)` is the wrapping operation; it has no overflow
  to prove.
- **Check.** `checked_add(x, 1)` answers `Option[int]`: `None` when the result
  does not fit, so the program can handle the edge case instead of stopping.
- **Clamp.** `saturating_add(x, 1)` stops at `int::MAX`.

If the operation should stay checked and only an unexpected input is the
problem, bound the operand first:

```yashy
fn main() {
    let x: int = 9223372036854775807;
    if x < 9223372036854775807 {
        let y = x + 1;
    }
}
```

The guard narrows `x` in the branch, so the sum is `9223372036854775807` at
most and the rule is silent.

Other ways to discharge it:

- subtract instead of adding a negative, when the two would cancel;
- bound the operands with a `requires`, so the function's callers owe the fact
  the body needs;
- return early at the boundary rather than computing past it;
- split the work so each step stays in range, such as summing in a smaller unit
  or checking before each step.

If the overflow can only happen for inputs you do not expect, a `requires` that
rules those inputs out is the honest fix: it moves the obligation to the call
site, where the caller can see the values it is passing.
